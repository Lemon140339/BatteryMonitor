# 设计说明

这份文档记录**为什么这样做**，而不是做了什么。做了什么看 README 和源码。
如果你接手这个项目（或者隔了几个月回来），先读这里。

---

## 目标与非目标

**目标**

- 在桌面上随时看到无线键鼠的电量
- 不依赖厂商驱动、不装后台服务
- 新增设备是改配置，不是改代码

**非目标**

- 不做灯光控制（各家协议差异过大，且需要写设备）
- 不做按键重映射（涉及驱动层，风险与收益不成比例）
- 不做跨平台（Windows 的 HID 与窗口 API 是设计前提）

---

## 为什么是"纯 HID 直读"

最初的需求是"把键鼠驱动整合成一个软件"。调研后结论是：

> 厂商驱动里真正私有的不是驱动，而是**协议**。
> Windows 的 HID 类驱动本身就统一了，厂商软件额外做的是私有功能。

所以整合的正确姿势不是"包一层驱动"，而是**直接说设备的话**。
协议通过 USB 抓包获得，只做读取，不写设备——这样既不碰驱动签名，也不碰反作弊。

---

## 协议事实

### 英菲克 IN10（被动推送）

- 接收器 `1D57:FA65`，接口 `MI_02&Col03`，报告长度 5 字节
- 帧格式：`03 93 40 <状态> <电量>`
  - `0x03` 报告 ID，`0x93` 设备号 147，`0x40` 电量状态码
  - 状态：1 正常 / 2 满电 / 3 充电中
- 设备主动推送，无需查询

### NDIY KY87（一问一答）

- 接收器 `0C45:FEFE`，接口 `MI_03`，报告长度 33 字节
- 发送：`00 20 01 00 ...`，第 31 字节为前 30 字节之和
- 回复：第 4 字节为电量，末字节为前 32 字节之和的低 8 位

### 抓包时踩过的坑

- **报告 ID 会被 USB 层剥掉**：抓包里看到 32 字节，实际写入要 33 字节（首位补 `0x00`）
- 校验和要算上报告 ID
- 长度用 caps 的 `InputReportByteLength`，不要用抓包长度

## 托盘与悬浮层：谁在什么时候出现

两个界面并存，分工明确：

| 形态 | 何时出现 | 为什么 |
|---|---|---|
| 托盘图标（电池 + 悬停提示 + 右键菜单） | 一直在 | 平时不挡视线，鼠标扫一眼就有数 |
| 右上角悬浮层 | 全屏时（默认） | 这会儿托盘被全屏窗口盖住，只能靠悬浮层 |

两者共用一个数据源，`WidgetApp` 每秒问一句「该显示谁」，窗口只是被动 Show/Hide。

### 托盘图标：一台设备一个电池

不合并成「一个电池代表整体最低电量」——那样看不出是哪台快没电了。
`MakeIcon` 按设备顺序竖着画 N 个电池，各自着色、各自填充，跟悬浮层的行序一致。

16×16 最多塞下 3 个；再多就退回单电池（取最差那台），明细交给 tooltip 和右键菜单。
设备上限本来就是少数几台，这个退化可以接受。

### 悬浮层为什么要每秒「顶」一次

全屏视频播放器之类的窗口**自己也是 topmost**。它一激活就排到 topmost 组的最前面，
于是我们的悬浮层被压在下面——表现就是「视频全屏时看不到，退出全屏的一瞬间又闪现」。

我们的窗口不能激活（`WS_EX_NOACTIVATE`，否则会抢游戏/播放器的焦点），
所以只能主动把 Z 序顶回去，具体做了三层：

1. `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)`：前台一变立刻重算，不等定时器；
2. 显示期间另开一个 **200ms** 的计时器只做 `SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE)`——
   有的播放器每帧都在给自己调 SetWindowPos，1 秒一次抢不过；
3. 每秒做一次「我是不是被挡住了」的检查（沿 Z 序列举，找第一个完全罩住自己的可见窗口），
   把对方的类名/标题写进 `--log`，用来定位到底是谁压在上面。

### 有些全屏应用根本盖不上去（系统限制）

**媒体播放器（UWP）全屏时，任何别人进程的窗口都进不了画面**，包括普通不透明窗口。

证据：写了一个对照程序，在屏幕右上角同时放两个窗口——A 用分层透明（产品的画法），
B 用普通不透明窗口，都置顶、都不抢焦点，每 2 秒从屏幕上抓自己那块数字（`--selfcheck` 同款算法）：

```
桌面        A(分层)=47   B(不透明)=50
视频全屏    A(分层)=0    B(不透明)=0      ← 两个都没了
退出全屏    A(分层)=47   B(不透明)=50
```

Z 序检查显示「上方没有窗口」（只有 shell 的 `ForegroundStaging`），
但屏幕上就是没有像素——说明窗口是「在 Z 序里」，只是**没有被合成**。

原因：UWP 播放器的全屏走了 DWM 的直通呈现（fullscreen optimization / direct flip），
屏幕直接显示应用自己的交换链，桌面合成层被绕过。加上去的窗口会被整层跳过。

这跟画法无关，换不透明、去掉分层都没用；要覆盖只能做 DLL 注入 + hook 应用的交换链
（RivaTuner / Steam 覆盖层那条路），代价远超这个项目。

**实践结论**：

- 浏览器全屏（F11 / HTML5 全屏视频）、VLC/MPV 这类普通窗口全屏 → 悬浮层正常；
- UWP 播放器（Windows 11 的「媒体播放器」）全屏 → 看不到，这是系统行为，不是 bug；
- 需要在这种应用里看电量，只能退出来看托盘。

### 悬浮层画在哪块屏

以前固定画在主屏右上角。视频在副屏全屏时，悬浮层其实画到了另一块屏幕上，
看起来就像「没显示」。现在 `FullscreenWatcher` 会给出全屏窗口所在的显示器矩形，
悬浮层跟着它走（没有全屏窗口时回到主屏）。

### 用原生 Shell_NotifyIcon，不用 WinForms 的 NotifyIcon

`.NET` 的 `NotifyIcon.Visible = true` **不会把失败告诉你**：注册失败时它既不抛异常也不报错。

踩过一次真实的坑：程序用 `NotifyIcon` 注册，没有异常，于是以为托盘可用 →
在「自动」模式下把悬浮层也藏了 → 用户**托盘和悬浮层都看不到**，
而日志还写着「托盘=可用」。实际上 `Shell_NotifyIcon(NIM_ADD)` 返回的是 `FALSE`，
`GetLastError` 是 5（ACCESS_DENIED）。

所以托盘改成直接调 `Shell_NotifyIcon`，以**返回值**为唯一真相
（[src/TrayView.cs](../src/TrayView.cs)），`Available` 就是这个返回值。

### 为什么不按「是不是管理员」决定要不要提权

托盘图标确实有权限门：这台机器的 explorer 以高权限运行，普通权限拿到的就是 `err=5`。

但不同机器、不同桌面外壳状态下结论会变，写死「必须提权」会让本来不需要的机器每次启动白弹 UAC。

所以**先真的注册一次再决定**（`Program.CanUseTray`，内部就是 `new TrayView(true).Attach()`）：

1. 成功 → 普通权限直接跑，不打扰用户；
2. 失败 → `runas` 重启自己一次（带 `--elevated` 防止循环）；用户拒绝 UAC 就继续跑，
   托盘不可用时自动退回「总是显示悬浮层」——用户至少能看到东西。

### 全屏怎么判断

**不用 `SHQueryUserNotificationState`。** 实测在这台机器上，前台只是一个 1296×828 的普通窗口时，
它也返回 `QUNS_BUSY`(2)；拿它当判据会让悬浮层乱闪。

改用「前台窗口矩形是否覆盖它所在的显示器」（`FullscreenWatcher`，容差 2px），
并排除本进程自己的窗口（点托盘菜单时前台是本程序，不能算全屏）。

### 独占全屏做不到

真正的 D3D 独占全屏会接管屏幕合成，分层窗口画不上去——这时右上角不可能出现悬浮层，
托盘也被游戏盖住。只有**无边框窗口化全屏**才有戏。文档里写明这条，别承诺做不到的事。

### 旧的权限实测记录（保留，作为排查参考）

| 启动方式 | 管理员 | 窗口站 | `Shell_NotifyIcon` |
|---|---|---|---|
| 普通双击 | 否 | WinSta0\Default | ❌ `err=5` ACCESS_DENIED |
| 计划任务（最高权限） | 是 | WinSta0\Default | ❌ `err=5` |
| UAC 提权 | 是 | WinSta0\Default | ✅ `True` |

结论仍然是：**托盘图标是权限问题，不是路径问题。**
计划任务那条路被否掉，是因为它属于另一个登录会话。

## 为什么锁死 C# 5 和零依赖

编译用的是 Windows 自带的 `csc.exe`（.NET Framework 4.x），它只支持 C# 5。

好处：

- 用户不需要装 SDK、不需要 NuGet
- 产物是一个不到 30 KB 的 exe，双击即用

代价：

- 不能用字符串插值、表达式体成员等新语法
- JSON 解析只能用 `System.Web.Extensions` 里的 `JavaScriptSerializer`

这条约束写在 `CONTRIBUTING.md` 里，因为它最容易让贡献者卡住。

## 配置模型

设备描述放在 `devices/*.json`，由 `Profile.cs` 反序列化，`DeviceWorker.cs` 按 `mode` 驱动。

两种模式：

| 模式 | 行为 | 适用 |
|---|---|---|
| `passive` | 打开设备，循环读，用 `match` 过滤出电量帧 | 设备主动上报 |
| `query` | 打开→写查询帧→读回复→校验→关闭 | 一问一答 |

设计取舍：

- **用 `match` 而不是固定长度**：同一通道上还有 DPI、配置回读等报文，靠特征过滤比靠长度可靠
- **校验只做 `sum8`**：覆盖了目前遇到的设备，真有 CRC8 再加
- **`iface` 必填**：自动扫描所有集合会让错误更难诊断，宁可让用户明确指定

配置错误不会静默失败：加载时校验，失败写 `config-error.log`，屏幕上显示红字。

## 运行时结构

```
Program.Main
  ├─ Application.EnableVisualStyles  必须早于任何窗口（托盘探测会建窗口）
  ├─ CanUseTray()                    能注册托盘就不提权，不能才 runas 重启
  ├─ ProfileLoader.Load(devices/)    解析 + 校验，产出 DeviceProfile 列表
  ├─ 每个 profile 起一个 DeviceWorker 独立线程，互不影响
  └─ WidgetApp（ApplicationContext） 每秒一次：
       ├─ 汇总 worker 状态 → TrayView.Update      图标 + 悬停提示 + 菜单
       ├─ FullscreenWatcher.IsForegroundFullscreen
       ├─ ShouldShowOverlay(tray, mode, fullscreen)
       └─ WidgetForm.Show/Hide + RenderNow
             └─ WidgetRender                      排版与绘制（纯 GDI+，不碰窗口 API）
```

`DeviceWorker` 只维护一个 `Percent` 字段，变化时触发 `Updated`。
UI 每 1000ms 读一次全部 worker 的状态重绘——**不做事件驱动重绘**，因为设备更新频率低，轮询更简单也更稳。

排版单独放在 `WidgetRender` 里，好处是能离屏画到 `Bitmap` 上核对对齐，
不需要真的开一个窗口（数字列按 `100%` 定宽就是在这里保证的）。

显示策略也刻意做成纯函数 `ShouldShowOverlay(trayAvailable, mode, fullscreen)`，
不碰窗口，可以直接用真值表验证：

| 托盘可用 | 模式 | 全屏 | 显示悬浮层 |
|---|---|---|---|
| 否 | 任意 | 任意 | 是（否则用户什么都看不到） |
| 是 | 自动 | 是 | 是 |
| 是 | 自动 | 否 | 否 |
| 是 | 总是显示 | 否 | 是 |
| 是 | 只留托盘 | 是 | 否 |

## 已知限制

- 键盘休眠时查询无响应，保留上次数值，5 秒后重试；
  连续 5 分钟都读不到才显示 `--`（`DeviceWorker.StaleLimit`）
- 查询类设备 30 秒轮询一次（再快会明显费电）
- 只支持一个配置文件对应一个设备，同一型号插两个会被后者覆盖
- 电量是设备上报的原始值，无法校准
- 独占全屏（D3D exclusive）下分层窗口不参与合成，悬浮层看不到；
  托盘也被全屏窗口盖住，要切出来才有
- Windows 11 把新托盘图标默认收进「^」溢出区，想常驻可见得手动拖出来
